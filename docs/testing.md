# 测试策略

---

## 一、总体思路

这个项目最容易出错的**不是 CRUD**，而是「多端算出的比分不一致」和「离线数据丢了/重复了」。
所以测试的重点放在三个地方：

1. **纯函数内核**（事件写入规划器、比分投影、比赛引擎）—— 这是所有正确性的源头，
   用大量单元测试覆盖边界；
2. **真实链路的闭环**（HTTP + Socket.IO 全真，不打 mock）—— 端到端证明「计分 → 观众看到」；
3. **前端离线代码的真实执行** —— 打包器在受限环境跑不起来时，仍能验证离线逻辑。

测试不追求覆盖率数字，追求「真机上会炸的场景都被钉住了」。

---

## 二、怎么跑

```bash
pnpm --filter @openhoopscore/api test            # 42 条单元测试
pnpm --filter @openhoopscore/api test:e2e        # 12 条端到端测试
pnpm --filter @openhoopscore/api test:all        # 全部 54 条
pnpm test:web-offline  # 前端离线链路 36 项断言
```

前置：`pnpm --filter @openhoopscore/api build`（前两条脚本已自动包含）。
前端验证脚本会在需要时自行拉起一个 API 实例（端口 3100）。

测试运行器用的是 **Node 内置 `node:test`**，不是 Jest/Vitest。
原因很实际：本机环境无法创建文件符号链接，pnpm 的嵌套依赖装不全，
Jest/Vitest 这类需要完整依赖树与原生二进制的工具跑不起来；
而 `node:test` 零依赖、且支持 `--test-isolation=none`（进程内运行，不需要 spawn 子进程）。
测试本身毫无缩水 —— 端到端测试用的是真实的 Socket.IO 客户端与真实 HTTP。

## 三、单元测试（42 条）

### 3.1 `assignment-planner.test.ts` — 事件写入算法（10 条）

整个平台最关键的逻辑集中在这里。覆盖：

| 用例 | 钉住的 bug 类型 |
|------|----------------|
| 首次写入按 `clientTimestamp` 升序分配 seq | 乱序提交导致时间线错乱 |
| 幂等：同一 `clientEventId` 重复提交只接受一次 | **重复计分**（断网重连最典型的故障） |
| 批内重复幂等键 → 只接受第一条，其余判为 duplicate | 客户端一次推了重复项 |
| 离线补传旧事件插入中间，后续事件整体后移 1 位 | 「补传后时间线错位」 |
| **同一批事件以任意顺序提交，最终 seq 完全一致** | 非确定性排序（多端结果不一致的根因） |
| 同刻跨设备事件按 `clientId` 稳定排序 | 顺序抖动 |
| 校验：球员不属于该队 / 节次非法 / 得分值非法被拒绝且不影响同批其它事件 | 脏数据污染事件流 |
| 容量上限拒绝 | 异常客户端刷爆存储 |
| `rankOf` 与 `plan` 结果一致 | 两种实现漂移 |
| 未来时间戳被夹到服务端时间 | 设备时钟错误打乱时间线 |

### 3.2 `projection.test.ts` — 比分投影（8 条）

前后端跑的是**同一个函数**，所以这些断言同时约束两端。
覆盖累计得分、分节得分、球员得分、撤销回退、撤销后重新得分、
全队犯规按节累计、暂停计数、节次推进与终场、乱序输入自动重排、空事件流初始状态。

### 3.3 `match-engine.test.ts` — 直播文案与统计（10 条）

这些是**观众端直接看到的内容**，错一个字现场就尴尬：

- 图文直播的比分快照随时间累加、最新在最前、时间格式为 `mm:ss`；
- 被撤销的事件不产生直播条目，且**快照比分正确回退**；
- 撤销栈最近在前、描述可读（「撤销 张三（主队） 的 3 分（第2节）」）；
- 已被撤销的事件不再出现在撤销栈（不能撤销一个已撤销的操作）；
- 球员统计（得分/犯规/三分/投篮方式分布）、在场状态由换人事件推导；
- 排行榜同分并列名次（1, 1, 3）；
- 里程碑检测（20 分、五次犯规离场），且**只在跨越那一刻触发一次**；
- 撤销全部得分后状态回到 0:0。

### 3.4 `json-file.store.test.ts` — 零依赖存储（8 条）

重点不是 CRUD，而是两条工程约束：

- **并发写入不丢数据**：60 个互不等待的写入请求同时打进来，
  断言「60 条全在、seq 互不重复、返回按 seq 升序」；
- **落盘原子**：重启实例后数据仍在、文件是合法 JSON；
- 数据文件损坏时**隔离旧文件**（改名留证据）而不是静默丢数据；
- 撤销把目标标记为已作废；
- 幂等命中的返回结构正确；
- `findExistingClientEventIds` 能支持客户端本地队列对账。

### 3.5 `share-code.test.ts` — 分享码（6 条）

现场用法是「大屏投二维码 + 计分员口头报码」，所以既要能扫，也要能手输：

- 字符集不含易混字符（`0O1IL`）；
- 大小写与空格不敏感；
- 支持三种真实入口：纯码 / `?code=` 链接 / `/m/` 短链；
- 无法识别时返回 `null`（**不猜**）；
- 拼链接不出现双斜杠。

## 四、端到端测试（12 条，`test/e2e/closed-loop.test.ts`）

**进程内启动真实 Nest 应用**，监听临时端口，用 `fetch` 与 `socket.io-client`
打真实网络。没有 mock —— 暴露的失败就是真实失败。

| 用例 | 验证的核心风险 |
|------|---------------|
| 健康检查暴露存储驱动与投影内核版本 | 多端排查「谁算错了」的依据存在 |
| 创建比赛返回分享码，能用分享码扫码进房 | 扫码闭环；错误码 `SHARE_CODE_NOT_FOUND` |
| **计分员写入后，已连接的观众立即收到新比分** | 实时性；且 REST 读到的权威状态与广播一致 |
| **离线优先：断网记录 → 恢复后批量补传 → 比分正确且不重复** | 最核心的痛点场景；含重推验幂等、对账、增量拉取 |
| **撤销：不删历史，只追加 void，比分回退且观众端同步收到** | 撤销的完整语义；含「再撤销返回 NO_UNDOABLE_EVENT」 |
| 鉴权：无口令写操作 403，观众端只读不受影响 | 防止观众伪造比分；Socket.IO 侧同样拦截 |
| 校验：球员不属于本场被拒绝且不影响同批其它事件 | 部分失败时不能整批丢弃 |
| 结束比赛后观众收到 `match:finished`，状态变 finished | 终场广播 |
| 无副作用试算与权威投影一致 | 防止两端算分不一致；且 preview 必须只读 |
| 观众带 `lastSeq` 加入时直接拿到缺失事件 | 断线重连省一次往返（`sinceSeq: 0` 的边界） |
| 归档后的比赛拒绝继续计分 | 历史不可变 |
| 球员榜按得分排序，能看到两队名单 | 观众端数据链路 |

## 五、前端离线链路验证（36 项断言）

`apps/web/scripts/verify-offline-engine.mjs`。

**为什么单独做这个**：打包前端需要 esbuild/SWC 的原生二进制，
而它们的 JS 封装通过「子进程 + 管道 stdio」与二进制通信，
在受限环境里必然 `spawn EPERM`。于是换一条路：
用 TypeScript 的**进程内** `transpileModule` 把前端真实的离线代码
（`src/offline/queue.ts`、`src/offline/derive.ts`）转成可执行模块，
补上最小浏览器垫片后对着**真实 API** 跑完整闭环。

覆盖：

1. **受限存储降级**：故意不提供 `indexedDB`，断言自动降级到 `localStorage`
   （隐私模式 / 老旧 WebView 分支），设备标识稳定可复用；
2. 管理后台链路：建比赛、分享码可扫码进房（大小写不敏感）；
3. **断网记录 3 次点击**：事件落本地（刷新不丢）、带幂等键、
   **本地立即推出 6:0**（乐观 UI），且断网期间请求确实被挡住；
4. **恢复网络批量补传**：3 条全接受、服务端权威比分与本地推导一致、
   队列被清空、对账能区分「已上行」与「未上行」；
5. **幂等**：重推同一批判为 duplicate，比分不变；
6. 本地 `void` 事件结构合法（离线撤销的构造正确）；
7. 撤销后比分回退、事件流一条没删、撤销描述可读；
8. 图文直播文案与快照回退正确、球员榜数据正确；
9. 队列生命周期：按比赛清理、**不同设备队列互相隔离**（同一台平板打多场的关键）。

## 六、没有覆盖的部分（诚实说明）

| 项 | 原因 | 建议 |
|----|------|------|
| Prisma 驱动的端到端测试 | 本机无 Docker/PostgreSQL | 有数据库后跑 `db:deploy` + 同一套 e2e（把 `STORAGE_DRIVER` 换成 prisma 即可） |
| 前端 UI 交互测试（点击、渲染） | 需要浏览器环境（Playwright），而 Playwright 的浏览器二进制在本机装不上 | 在正常环境补 Playwright |
| 小程序端运行测试 | Taro 构建依赖 SWC 原生二进制，本机受限 | 正常开发机上构建后在微信开发者工具里人工验证 |
| 长时间压力测试 | 单机环境不具备代表性 | 上线前用 k6/autocannon 打 `/events` 与 Socket.IO |
| 多实例（Redis adapter） | 尚未实现横向扩展 | 见 [roadmap.md](roadmap.md) |

## 七、新增测试时的注意事项

1. **写测试前先想清楚「真机上会怎么炸」**。这个项目里 4 次测试失败有 3 次是
   **我的断言写错了**（比如以为撤销会撤最早那条，实际撤的是最近那条；
   以为批内重复会进 `rejected`，实际进的是 `duplicates`）。
   断言前先在设计层面确认语义，别照着直觉写。
2. **不要为了让测试通过而放宽断言**。发现实现与预期不符时，
   先判断是实现的 bug 还是理解错误 —— 上面那次「60 并发不丢数据」就是实现对了、直觉错了。
3. **端到端测试里的事件必须复用同一个 draft 对象**。
   测试夹具的 `clientEventId` 是随机生成的，构造「作废指向某事件」时如果重新
   调用一次 `draft()`，指向的就是另一条事件了（这个坑踩过一次）。
4. **超时给足**。现场网络差是设计前提，端到端里的 ack 等待设成 6–8 秒才稳。
