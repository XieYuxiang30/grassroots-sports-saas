## 1. 全局结构

```
                    ┌──────────────────────────────┐
                    │  packages/contracts          │
                    │  事件模型 · 计分内核 · 协议    │  ← 唯一真相来源
                    └───────────┬──────────────────┘
            编译期同源引用       │       编译期同源引用
        ┌───────────────────────┴───────────────────────┐
        │                                               │
┌───────▼─────────────┐                      ┌──────────▼─────────────┐
│  apps/api（NestJS）  │◄──── Socket.IO ─────►│  apps/web（React SPA）  │
│  · 计分服务          │◄──── REST ──────────►│  · 计分台（离线引擎）    │
│  · 比赛引擎（投影）   │                      │  · 观众端 / 大屏        │
│  · 实时网关          │                      │  · 管理后台            │
└───────┬─────────────┘                      └──────────┬─────────────┘
        │                                               │
┌───────▼─────────────┐                      ┌──────────▼─────────────┐
│ 存储驱动（可替换）    │                      │ 本地队列（IndexedDB）   │
│ json / prisma /mem  │                      │ 乐观投影（同一个内核）   │
└─────────────────────┘                      └────────────────────────┘
```

**关键点**：计分内核（`packages/contracts/src/score.ts` 的 `projectMatch`）是**纯函数**，
前后端引用同一份代码。因此「本地显示 12:10、服务器显示 10:10」这类经典 bug
在结构上就不可能出现 —— 除非两端事件集合不同，而那是同步层要负责的事。

## 2. 为什么是事件溯源（Event Sourcing）

方案里明确要求「切忌只存最终比分」。原因在基层赛事的现场非常具体：

| 需求 | 只存比分 | 事件溯源 |
|------|---------|---------|
| 计分员点错要撤回 | 无法知道上一步是什么 | 追加 `void` 事件，比分自动回退 |
| 中途断网后补传 | 无法合并两段时间线 | 按客户端时间戳插回正确位置 |
| 观众中途进场 | 只有比分，没有过程 | 事件流 → 图文直播，可回看 |
| 赛后复盘 / 争议 | 无从查证 | 完整审计链（谁在何时撤销了什么） |
| 球员数据榜 | 需要另建统计表并保持同步 | 从同一份事件流投影，天然一致 |

`GameEvent` 是唯一的权威表，**没有** `home_score` / `away_score` 这类字段。
`MatchState`（比分、球员统计、节次、犯规）全部是投影结果。

### 撤销的语义

```ts
// 不删除，追加指向：
{ type: 'void', payload: { targetEventId: '<被撤销的事件 id>', reason: 'scorer_undo' } }
```

投影时先扫一遍收集 `voided` 集合，再跳过被作废的事件。
比分、球员数据、图文直播会自动回退，历史事件一条不少。

## 3. 确定性时钟：离线多设备合并

**问题**：计分员断网 10 分钟，本地攒了 20 条事件；与此同时备用平板也记了几条。
恢复网络后，先到的可能是**后发生**的事件。

如果 `seq` 按「到达服务器的顺序」自增：

- 落后的补传会插在中间 → **所有后续事件的 seq 都要改**；
- 关系库上直接撞 `(match_id, seq)` 唯一约束；
- 已经推给观众端的增量游标全部作废，只能全量重推。

**解法**：把 `seq` 定义成**确定性排名**，排序键与「何时到达」完全无关：

```
排序键 = (clientTimestamp, clientId, clientEventId)
seq(E) = 1 + |{ F : 排序键(F) < 排序键(E) }|
```

于是：

- 同一事件无论何时、以何顺序到达，算出的位置都一样（**幂等**）；
- 补传旧事件只需插入一个空位，已有事件的相对顺序不变；
- 观众端可以放心用 `seq` 做增量游标。

代价是补传插入时后续事件会整体后移（JSON 驱动会重排并重编号，
Prisma 驱动用 COUNT 算排名、允许 seq 出现空洞）。两种驱动都会把
`reordered = true` 返回给客户端，客户端据此重新拉取直播流。

> 实现见 `apps/api/src/store/assignment-planner.ts`，测试见
> `apps/api/test/unit/assignment-planner.test.ts`（含「同一批事件以任意顺序提交，
> 最终 seq 完全一致」的确定性断言）。

### 客户端时间戳的兜底

设备时钟可能不准。`normalizeClientTimestamp` 只做**上界保护**：
超过未来 24 小时的时间戳夹到服务端时间；不做下界修正 ——
因为「过去的时间」正是离线补传的正常形态。

## 4. 离线优先（Offline-First）

### 数据流

```
点击 ──► 生成 clientEventId（幂等键）
      ──► 写入 IndexedDB 队列（await 落盘后才返回）   ← 此刻起断电也不丢
      ──► 用 projectMatch 立刻重算比分                ← 乐观 UI
      ──► flush()：Socket.IO 提交，失败退回 REST
            ──► accepted / duplicate → 出队
            ──► rejected → 留在队列并记录原因（UI 提示人工处理）
            ──► 网络异常 → 全部保留，5 秒后指数退避重试
```

### 存储分层

`apps/web/src/offline/queue.ts` 按可用性依次降级：

1. **IndexedDB** — 事务性、容量大，平板被强杀不会留半条记录；
2. **localStorage** — 隐私模式 / 老旧 WebView 的兜底，容量约 5MB；
3. **内存** — 都没有时的最后退路，UI 会明确提示「存储受限」。

UI 顶部状态条如实显示当前状态，不假装在线：

- `已连接 · 实时同步中`
- `离线记录中 · N 条待同步（正在补传）`
- `未连接服务器 · 记录会先存在本机，恢复后自动补传`

### 为什么队列不用 localStorage 当主力

现场一场比赛轻松几百条事件，加上后续要扩展（暂停原因、犯规对象明细等），
localStorage 的 5MB 与「整串 JSON 覆盖写」都不合适。IndexedDB 的事务语义也更安全。

## 5. 存储驱动可替换

`StorePort` 接口有三种实现，业务代码只依赖接口：

| 驱动 | 场景 | 特点 |
|------|------|------|
| `json`（默认） | 演示、单机部署、学生机 | 零基础设施；**原子写**（tmp + rename）+ **写串行化**（Promise 队列）+ 写合并 |
| `prisma` | 生产 | PostgreSQL；幂等由 `(match_id, client_event_id)` 唯一约束兜底 |
| `memory` | 单元测试 | 进程退出即清空 |

三种驱动共享**同一个** `AssignmentPlanner`，保证写入语义完全一致 ——
这是「换驱动不用改计分逻辑」的关键，也是可以拿 JSON 驱动做端到端测试的底气。

### JSON 驱动为什么不是玩具

- 原子写：先写 `hoop-store.json.<pid>.tmp` 再 rename，断电不会留下半个 JSON；
- 写串行化：所有变更经一条 Promise 队列，并发请求不会互相覆盖
  （`test/unit/json-file.store.test.ts` 里有「60 个并发写入一条不丢、seq 不重复」的断言）；
- 文件损坏时不静默清空，而是改名隔离留证据，再以空库启动。

## 6. 实时通信设计

### 房间

| 房间 | 成员 | 用途 |
|------|------|------|
| `match:{matchId}` | 所有人 | 比分广播 |
| `match:{matchId}:scorers` | 仅计分员 | 撤销栈等计分端专属事件 |

### 服务端推送

| 事件 | 内容 |
|------|------|
| `events:committed` | 增量事件 + 比分牌（观众端零延迟更新） |
| `state:patch` | 完整 `MatchState`（节次、比赛状态变化） |
| `feed:appended` | 图文直播文案 |
| `undo:applied` | 撤销结果 + 新撤销栈 |
| `scorers:presence` | 在线计分设备（多设备同时计分时提示人工核对） |
| `match:finished` | 终场比分 |
| `player:highlight` | 球员里程碑（20 分、犯满离场） |

### 为什么 Socket.IO 而不是原生 WebSocket

场馆网络经常只放行 80/443，纯 WebSocket 会被中间设备掐断。
Socket.IO 自带「WebSocket 失败自动降级长轮询」、房间语义、
重连与 ack 回调 —— ack 尤其关键：计分端必须拿到明确结果才知道该不该清本地队列。

心跳放宽到 `ping 20s / timeout 25s`（`SOCKET_PING_INTERVAL` / `SOCKET_PING_TIMEOUT`），
避免观众在信号弱的角落频繁掉线。

### 广播收口

REST 写入（离线补传）与 Socket.IO 写入都经过 `RealtimeService.publishSubmit`。
如果广播只写在 Socket 分支里，用 REST 补传的事件就不会出现在电视大屏上 ——
这是很容易踩且很难查的坑。

### 依赖方向

`RealtimeService` 需要业务服务，业务控制器又需要它来广播，直接互相 import 会循环依赖。
解法是依赖倒置：`apps/api/src/realtime/realtime.ports.ts` 定义 `ScorerPort` /
`MatchesPort` 与 `RealtimeRegistry`，业务模块在 `onModuleInit` 时把自己注册进去。
依赖方向始终单向：业务模块 → 实时模块。

## 7. 前端：一个 SPA 承载三种角色

| 路由 | 角色 | 布局要点 |
|------|------|---------|
| `/score/:matchId` | 计分员 | 平板横屏；大按钮、单手可达；撤销固定在顶部工具条；支持键盘 `1/2/3`、`Shift+1/2/3`、`Ctrl+Z` |
| `/live/:matchId` | 观众 | 手机竖屏；比分首屏最大；断线不白屏，保留最后比分并显示「连接中」 |
| `/display/:matchId` | 大屏 | 无交互；字号 `clamp()` + `vw`，5 米外可读；底部滚动最新图文 |
| `/admin` | 管理员 | 名单支持**批量粘贴**（`4 张三` / `张三 4` / `4、张三` 都能识别） |
| `/m/:code` | 扫码 | 零点击自动进直播间 |

### 为什么名单要支持批量粘贴

现场最常见的做法是领队在微信里发一段名单过来。让管理员一个个点「添加球员」
填号码和姓名，是真正会让人放弃使用系统的环节。

### 口令与权限

观众端**只读、不需要口令** —— 这是「扫码即看」的前提。
计分与撤销必须带口令（REST 用 `x-scorer-passcode` 头，Socket.IO 用 payload 字段），
服务端统一在 `ScoringService.assertScorer` / `RealtimeService.assertScorer` 校验。

> 口令是**共享密钥**级别的最小可用方案，适合单场赛事。要做多用户与权限体系，
> 见 [roadmap.md](roadmap.md)。

## 8. 有意为之的取舍

| 取舍 | 原因 |
|------|------|
| 秒表走动不是事件，只在 `state:patch` 里广播 | 若做成事件，一场比赛会写入上千条无意义记录，把事件流和存储刷爆。节次切换才是权威事件 |
| 球员统计的「在场状态」由换人事件推导，无换人记录时退化为首发 | 基层赛事常常不记换人，强行要求会让人放弃使用 |
| 事件里允许 `playerId = null` | 很多场次只记团队得分。强制指定球员会阻断计分，比缺失数据更糟 |
| 分享码 6 位、去掉易混字符 | 现场要能口头报码；10 亿组合对单机部署足够 |
| 撤销默认只撤最近一步，可传 `steps` 连撤 | 计分员最常犯的是「连点两下」，一步一撤比「撤销到某条」更符合直觉 |
| 比赛上限 `MAX_EVENTS_PER_MATCH = 20000` | 防止异常客户端刷爆存储；正常一场比赛约 200–600 条 |

## 9. 数据模型要点

完整定义见 `apps/api/prisma/schema.prisma`。核心表的几个索引各有明确用途：

```prisma
@@unique([matchId, clientEventId], name: "game_events_idempotency")  // 幂等兜底
@@unique([matchId, seq])                                            // 权威顺序 / 增量游标
@@index([matchId, clientTimestamp])                                 // 按时间线回放、冲突排查
@@index([matchId, teamId])                                          // 按队伍聚合
@@index([matchId, playerId])                                        // 按球员聚合
```

`SyncBatch` 表记录每次离线补传的批次与离线时长 ——
现场排查「到底断了多久、补传了多少条」时非常有用，也是后续做网络质量统计的数据源。
